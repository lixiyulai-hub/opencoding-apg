# OpenCoding 完整 AI Coding 治理工作流：架构与执行路线

日期：2026-10-10
状态：产品方向与后续验收架构；不是完整产品已经交付的声明。

## 产品边界

OpenCoding 服务于刚开始用 AI 编程、不会写代码的用户。用户描述目标、用户和使用场景后，OpenCoding 主动澄清需求，判断平台、架构和项目能力，生成项目专属文档与任务图，再让 AI coding agent 按受控任务执行。它贯穿需求到交付的治理工作流，不是离线 APG 演示或测试夹具。

**Agent 是执行引擎；OpenCoding 是决策、编排与验收系统。** OpenCoding 负责保存项目事实和未决问题、将任务绑定到获准范围、组织执行顺序、检查 agent 返回的产物、编排验证和独立审核、保留失败与恢复证据。用户不需要安装 Docker Desktop GUI、MCP 服务或特定 IDE 插件作为 OpenCoding 的产品前提。具体 agent 和模型仍须经过对应接入与能力验收。

OpenCoding 可以为需要服务端、数据库、登录、支付、消息、后台、文件或部署的下游项目设计任务和 Gate。方案中出现这些能力，不等于 OpenCoding 已替用户接通服务；真实凭据、费用、数据访问、外部写入、部署和发布必须按具体动作暂停并取得人工确认。

## 端到端结构

| 阶段 | 输入 | OpenCoding 的责任 | 可检查产物 |
| --- | --- | --- | --- |
| 1. 想法与澄清 | 目标、用户、场景和回答 | 追问缺失信息；区分已确认事实、用户否定、未知、推断和假设 | 带来源与版本的需求会话 |
| 2. 方案判断 | 已澄清的需求与能力约束 | 建议平台、客户端/服务端形态、技术方案及 API、登录、支付等能力需要；说明理由、代价、未决项 | Recommendation、决策记录、待确认事项 |
| 3. 项目工作包 | 已确认或显式标为草案的方案 | 按项目生成不同职责的规则、记忆、需求、架构、计划、测试和回滚文档；构造依赖无环的任务图和执行波次 | 项目专属文档、TaskPlan、依赖图、验收条件 |
| 4. 授权预览 | 任务、目标仓库和拟写范围 | 展示变更目标、动作、输入摘要、外部影响、测试与恢复方式；使确认绑定本次具体范围 | Preview、范围摘要、授权/Gate 状态 |
| 5. Agent 执行 | 已派发的具体任务与最小必要上下文 | 经适配器交给所选 agent；记录派发、运行、取消、超时和结果；把返回产物留在受控候选区 | 带 task/run/host/plan 绑定的候选产物与执行记录 |
| 6. 验证与审核 | 候选产物、任务验收标准和项目验证命令 | 运行获准的验证；由独立审核步骤检查范围、需求符合度、安全性和证据；失败时冻结而不是伪报成功 | 测试结果、审核发现、证据摘要、失败状态 |
| 7. 修复与恢复 | 结构化失败与审核发现 | 形成受限修复任务；按预算重试；检查输入漂移、重复结果和断点；修复后重新验证与审核 | 修复 attempt、Requeue/恢复记录、回滚结果 |
| 8. 交付 | 通过的产物与全链路记录 | 汇总改动、测试、审核、限制、未决项和恢复点；将公开发布或生产动作交给人工 Gate | 最终交付摘要与可追溯证据 |

核心数据链应保持同一来源：

`Session/事实 → Recommendation/决策 → 项目文档 + TaskPlan → Preview/授权摘要 → Agent Task/Run → Candidate → Verification + 独立 Review → 修复/Requeue → Delivery`

每个阶段用稳定 ID 和内容摘要绑定其上游输入。上游需求、计划、授权范围或目标文件发生变化时，下游结果标记为 stale 并重新检查；不得复用旧通过状态。TaskPlan 只代表待办计划，不能代替 agent 实际运行记录或验收结果。

## Agent 执行边界

Agent 是可替换的执行引擎；OpenCoding 不依赖 Docker GUI 或某个 agent 品牌。接入层必须将 OpenCoding 的有界任务转成明确的 host 请求，并把响应规范化回同一任务状态机。建议的适配协议至少表达：

- `host_id`、适配器版本和经验证的能力集；
- `task_id`、`run_id`、任务/计划摘要、项目 root 标识和允许的文件范围；
- 用户目标、任务输入、输出路径、完成条件、验证步骤、重试上限与期限；
- queued/running/succeeded/failed/cancelled/timed_out/unknown 等明确状态及状态更新时间；
- 候选文件、摘要、agent 自述和结构化错误分开保存，不能把 agent 自述当成验收证据；
- 幂等键、重复/迟到响应处理、取消语义、超时后查询与恢复；
- 凭据经受控通道提供，禁止进入 prompt 日志、普通 receipt、生成文档或错误消息。

Host 不能表达必需的路径限制、状态绑定或恢复语义时，OpenCoding 必须降低能力、要求人工处理或拒绝该类任务，不能静默退化为任意 shell 执行。每个 host 单独维护 `planned`、`contract-tested`、`live-verified` 等证据状态；一款 host 通过不能推导所有 agent 兼容。

Docker 或其他隔离执行器只是一种可选候选执行后端。若项目选择它，要单独验证引擎可用、文件范围、网络边界、退出状态和资源清理。GUI 启动与否不构成 OpenCoding 产品 Gate，也不证明 AI coding 工作流成功。

## 生成级后续事务与依赖顺序

这里的生成级是指：从一个项目的已确认需求开始，产生并交付经过 agent 执行、测试和审核的代码变更。完成每个阶段都需要相应源代码、自动化测试和可复核运行证据；仅有架构文档或单元测试不算端到端通过。

| 顺序 | 事务 | 具体执行任务 | 验收 Gate 与依赖 |
| --- | --- | --- | --- |
| G0 | 工作流契约与证据基线 | 固定核心状态、ID/摘要绑定、候选与最终产物边界、失败分类、人工 Gate 规则；将现有代码路径和历史证据逐项映射到本路线 | 本文为方向基线；本事务后续还需形成可执行验收矩阵。不得以历史 JSON 状态推算总进度 |
| G1 | 澄清到任务图的项目级贯通 | 用多种项目需求校验回答修改、否定、未知、矛盾的传递；确认平台/能力决策与项目专属文档、业务任务图使用同一 session revision 和事实来源 | Recommendation、文档、TaskPlan 可追溯；未知项不会伪装成用户确认；无关能力不会被强行安排 |
| G2 | 统一 Agent Adapter 合约 | 定义 provider/host 身份、capability discovery、任务请求/响应 schema、状态查询、幂等、取消、超时、错误和恢复协议；实现首个受支持 host adapter 与 conformance tests | Mock 合约测试先通过；真实 host live check 单独标记。此阶段不声称通用 agent 兼容 |
| G3 | 通用项目生成与候选事务 | 将已采用 TaskPlan 的业务任务映射到 agent 执行包；把输出写入隔离候选区；验证允许路径、文件大小/格式、输入摘要、文件漂移和重复响应；确认后执行受控落盘并留 preimage/receipt | 不覆盖未授权文件；失配、越界、响应不全、provider 额度错误均失败关闭；该事务不得被固定示例项目专用逻辑替代 |
| G4 | 真实验证与独立审核 | 为每个生成任务运行项目声明的测试；定义独立 reviewer 输入只包含任务标准、diff 和必要上下文；将 review findings 结构化并绑定候选 digest | 失败测试或未处理的 blocker finding 不能交付；reviewer 不得把 generator 的口头成功当证据；审核步骤不可用时明确暂停 |
| G5 | 有界修复、冻结与断点恢复 | 将失败变为最小修复任务；设定请求/轮次/时间上限；覆盖 host 断连、超时后迟到响应、重复投递、进程中断、用户改文件、回滚部分失败与恢复后零重复 AI 请求 | 状态与 receipts 一致，依赖任务冻结/解冻正确；超过上限停止并说明人工下一动作；不修改历史 receipt 来补造成功 |
| G6 | 首个真实项目端到端验收 | 从中文需求开始，完整走澄清、方案、文档、任务波次、用户确认、agent 生成、自动测试、独立审核、必要修复、最终交付；至少选取一个不含真实外部服务的真实用途项目 | 由未参与实现的复核者按验收矩阵逐项检查；保留运行 ID、版本、测试与失败记录。合成项目结果不能代替此 Gate |
| G7 | 新手体验与发布准备 | 让目标用户独立完成首次旅程；记录需求补充次数、误解、失败恢复与求助点；检查安装、说明、错误提示、隐私和限制；之后再准备正式发布 | 新手验收依据预先定义的成功标准；生产服务、凭据、费用、远程 Git 和公开发布各自保留人工 Gate |

依赖关系为 `G0 → G1 → G2 → G3 → G4 → G5 → G6 → G7`。G2 可以用模拟 adapter 先完善合约测试；G3–G6 的真实链路必须使用同一个已验证 host 身份和可关联的运行记录。按需连接登录、数据库、支付、通知、存储或部署的工作是下游项目能力分支，由需求图决定并受各自 Gate 控制，不应变成所有项目都要安装的 OpenCoding 依赖。

## 贯通验收矩阵

首个真实项目端到端 Gate 至少检查以下场景，使用合成凭据和不触及真实外部服务的项目：

1. 正常路径：中文需求经过澄清、方案、文档和任务图，agent 输出候选，测试与独立审核通过后才形成交付。
2. 需求变化：改答或新增事实会更新 revision/digest，使旧候选、预览、审核和批准状态失效。
3. 明确否定：用户说“不需要登录/支付/联网”时，不生成相应外部接入任务，也不将其作为执行授权。
4. 任务失败：测试失败后任务冻结，产生有界修复工作；验证失败不能靠 agent 自报成功越过。
5. Host 故障：超时、断连、限额、无效 schema、响应截断、迟到/重复响应都有明确状态，无重复落盘或假成功。
6. 用户改动与恢复：目标文件漂移时拒绝覆盖；重启恢复能复核输入和收据，不重复已证实成功的 AI 请求。
7. 审核失败：独立 reviewer 的 blocker finding 阻止交付，修复后以新候选摘要重新运行测试和审核。
8. 外部 Gate：当计划需要真实密钥、费用、服务、部署、远程 GitHub 或公开发布时，在动作发生前呈现具体范围并等待人工确认。

## 宣传边界

可以介绍 OpenCoding 的目标定位、已有需求/规划/治理模块，以及有明确范围说明的合成生成恢复示例。完整生成级工作流在 G2–G7 逐项通过并形成独立复核证据之前，不能描述为已完成商业级端到端交付，也不能声称支持所有 provider/agent、任意平台、自动部署或零人工的外部操作。

本文件不修改历史 receipts、旧 delivery JSON、AGENTS.md 或其进度字段。后续执行以代码、测试输出和源版本绑定的事务证据更新实际状态。
