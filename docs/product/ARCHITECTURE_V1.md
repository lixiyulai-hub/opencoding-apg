# OpenCoding 产品化架构 V1

日期：2026-09-05。状态：实施设计，不是完成声明。
本设计面向 OpenCoding 本身，不把任何用户下游项目当成公开产品案例。

## 产品目标与承诺边界

小白用中文描述目标、用户和场景；系统追问业务问题而非要求选框架，
给出平台和具体技术方案，说明成本、维护负担与尚未确认的事实，
生成真正各司其职的项目文档，拆解业务任务、依赖和执行波次，
在授权范围内实际写文件、执行、验证、失败恢复。
外部费用、凭据、真实数据、服务连接和公开交付需要与当前方案绑定的确认。

最终产品不是只输出 JSON 的模拟器。现有 scripts 保留为兼容参考和回归证据；
新实现进入独立的 opencoding 包，先在隔离工作树开发，集成审核后才回写原项目。
原 .governance 历史、旧 Ledger、receipts、snapshots 和无关文件不迁移、不清理。

“所有能力”意味着所有下列验收项有实现及证据，不意味着任意未知需求都能
无人监督自动完成，也不意味着拿到一次同意后可永久支配外部账号和资金。
Windows/macOS/iOS/Android/Web/微信小程序/CLI 均覆盖方案建议；
原生构建、签名和商店交付必须有对应平台环境的实测证据，不能由 Windows 模拟通过替代。

## 六层架构

1. 交互层：中文 CLI 向导作为第一个真实入口，随后提供本地 Web 工作台。
   支持继续上次会话、改答案、看方案差异、查看任务进度与恢复，不暴露内部 JSON 给小白。
2. 决策层：结构化需求模型 + 会话状态机 + 可版本化技术方案目录。
   确定性解析只作输入提案；否定、冲突、未知明确区分。用户回答改变模型与计划版本。
   可选模型适配器以后补充复杂语义，不允许未验证模型输出直接变成执行命令。
3. 文档与计划层：按需求选择文档，分别渲染执行规则、决策记忆、产品范围、
   架构、数据模型、接口、权限、支付/通知/运维说明、计划、测试与回滚。
   任务图采用依赖拓扑，包含业务任务、输入、精确产物、动作类型、验收与重试策略。
4. 治理层：版本化 ActionContext、审批摘要绑定、路径检查、前后哈希、
   无覆盖证据、并发与漂移阻断、预映像、原子替换、失败恢复。
   可预览和讨论外部能力；真正执行外部动作才由执行边界作审批判定。
5. 调度与执行层：持久任务状态机，依赖满足才派发；命令只来自受审计的类型化动作，
   不拼 shell；超时、退出码、取消、崩溃恢复、失败冻结、限次重试和幂等均实测。
   先完成本地受控示例，再实现受控 AI coding Host 适配器。
6. 集成层：服务器/数据库/API/登录/支付/通知/后台/文件存储连接器。
   分开标注 planned、implemented、contract-tested、live-verified、production-ready。
   未激活的真实连接器显示“未接通”，不返回伪成功。

## 本项目实现取舍

- 核心使用现有 Python 标准库生态，形成可安装 opencoding 包；不靠全局 skills 安装才能启动。
- 状态存储使用本地 SQLite，采用事务和显式迁移；审计产物与原始项目证据分离。
- 文件写入先预览，执行时复查路径与前映像；不能把 pathlib 的一次检查称为操作系统沙箱。
- Web 工作台仅绑定回环地址，并验证 Origin、Host、请求令牌、路径范围和请求大小。
  不使用 Python 开发 HTTP 服务冒充可直接暴露公网的生产服务。
- 默认本地项目示例不需要网络、账号或付费；支持真正生成、运行、测试与恢复。
- 技术方案目录给出具体语言、框架、存储、版本依据、适用条件和替代方案。
  版本未核实必须标记未核实；不把“关系型数据库”当成已经完成选型。
- 开放式中文理解不能用扩大关键词表宣称完全解决：有结构化追问兜底和冲突确认。
- CLI 与 Web 共用服务层，不能各自重新实现 Gate、选型、任务状态。

## 核心用户旅程

启动 -> 输入想法 -> 少量分轮业务追问 -> 系统推荐方案 -> 修改/确认方案 ->
查看按需文档与动作预览 -> 授权本地范围 -> 实际生成 ->
执行与验收 -> 展示可运行结果 -> 失败恢复或下一阶段。

已讨论支付、数据库等业务需求不等于请求实际接通服务。
确认页必须说明“连接谁、做什么、读写什么、费用上限、如何撤回”。
一个方案可以合并相关确认，但摘要变化、范围变化、过期或撤销后必须重新确认。
秘密值不进入命令行、日志、数据库明文、文档、receipt 或可公开的异常消息。

## 安全与故障模型

- 输入误解：否定、冲突、歧义保留来源和状态；未答问题不能被高置信度默认值抹掉。
- 路径攻击：绝对路径、目录穿越、大小写别名、符号链接、junction/reparse、
  硬链接、保留路径和写入前后漂移必须测试，做不到强保证时明确拒绝或声明限制。
- 审批重放：批准绑定 root、plan digest、action digest、成本/数据范围、有效期及撤销状态。
- 写入故障：先持久 preimage 和日志；发生部分写入后明确恢复状态，不返回完整成功。
- 并发：同一目标事务互斥；读改写使用版本检查，两个任务不可静默覆盖彼此。
- 工具失败：首次失败阻断依赖任务；真实退出结果与模拟结果严格分开。
- 任意模型输出：默认不可信，只能产生经 schema 验证的候选计划；不具有授权能力。

工作树任务结束不等于验收：必须提交代码、测试输出、限制和提交号。
协调者审查 exact diff，集成到隔离仓库，运行跨模块测试，再做原项目回写预览。
不自动 push，不把本地 seed 或用户项目名称/历史证据发布到远端。

## 验收原则

见 DELIVERY_PLAN_V1.json 的十二项交付标准。测试名、运行环境、真实产物和复现命令
均需留存。现有 46 项测试及 Independent Review PASS 只作旧夹具基线。
默认 unittest 必须发现非零数量测试；零项测试即验证失败。
至少五名未参与开发的零基础用户完成事先定义的首次旅程测试，记录成功率与求助次数；
该人为体验证据不得由代理自评冒充。
